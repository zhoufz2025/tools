# 基金代销管理台入账差错补处理 — 需求说明书

> 文档说明：本文从业务视角描述管理台「入账差错补处理」能力。技术实现见同目录《管理台入账差错补处理-功能逻辑实现.md》。入账主流程见《基金入账流程分析.md》。
>
> 分析范围：`ifmCCxglDxfundErrQuery` 差错查询目录下，**处理 `tbdxfundsquareerr`（入账差错表）** 的菜单。重点菜单：资金清算差错记录查询（`ifmCCxglDxfundSquareErrMenu.vue`）。
>
> 分析基准：GIT-IFM6.0 标准实现；银行个性化以该行 Bean / Vue / SQL 为准。

## 1. 背景与目标

### 1.1 业务背景

基金代销日终（或日间）将 TA 确认后的资金通过主机入账。主机处理入账文件后，失败记录以「主机入账差错文件」（标准文件名 `bkerrsquare.{taCode}.{YYYYMMDD}`）回盘。系统将失败明细落入 **`tbdxfundsquareerr`（入账差错表）**，并回写资金清算表 `tbdxfundsquare` / `tbdxfundhissquare` 的入账状态。

柜员需要在管理台：

1. 查询入账失败明细及失败原因；
2. 修正账号等信息后重新发核心入账（补处理）；
3. 对已线下处理、无法再发核心的记录做强制成功 / 强制失败；
4. 对无法入客户账的记录入挂账账号；
5. 对超时未知记录向核心查证结果并同步本地状态。

### 1.2 建设目标

| 目标 | 说明 |
|------|------|
| 可查 | 按流水、产品、日期、客户标识查询入账差错，展示失败原因、账务状态、补处理状态 |
| 可补 | 对未处理差错重新发核心入账，支持换卡（参数控制） |
| 可强制 | 线下已处理场景允许强制成功 / 强制失败，不发核心 |
| 可挂账 | 上账方向（`liqu_dir=1`）允许入产品挂账账号 |
| 可同步 | 超时未知（`status=8`）可向核心查证并回写清算状态 |
| 可批量 | 文件模式：勾选记录生成补处理文件发核心，再获取结果回盘 |
| 可追溯 | 补处理操作员、结果说明、新账号等信息落差错表 |

### 1.3 不在本需求范围

以下同目录菜单**不处理** `tbdxfundsquareerr`，本文仅作边界说明：

| 菜单 | 实际数据表 | 业务 |
|------|------------|------|
| 份额对账差错 | `tbdxfundshareerr` | 份额对账调账 |
| 核心对账差错 | `tbdxfundbkcompdetail` | 主机对账差错补处理 |
| 解冻扣款差错 | `tbdxfundjdkkresult` | 解冻扣款结果解冻 |
| 资金对账差错 | `tbdxfundpaymentcomperr` | 资金入账日调整 |
| 理财账户补处理 | `tbassetacc` | 理财账户补处理 |
| 江南盈对账差错（ReUneven） | `tbdxfundtransreq` | 余额宝类对账查询 |

## 3. 业务对象

### 3.1 入账差错表 `tbdxfundsquareerr`

入账失败明细表。主键：`(square_date, serial_no, seq_no)`。

公共片区、交易片区各有一份：管理台查询默认落**公共库**；补处理联机在**交易片区**改清算表，并回写差错表，再由 T211213 同步回公共。

### 3.2 资金清算表 `tbdxfundsquare` / `tbdxfundhissquare`

按内部客户号分片。差错行通过 `serial_no` 关联清算流水：

- 参数 `SQUARENO_IS_SERIALNO=0`（默认）：`err.serial_no = square.square_no`
- 参数 `SQUARENO_IS_SERIALNO=1`：`err.serial_no = square.serial_no`

清算表 `status`（字典 `K_RZBZ`）是「账务状态」，差错表 `reserve1`（字典 `K_CCCLZT`）是「补处理状态」，二者配合使用。

### 3.3 状态字典

**账务状态 `K_RZBZ`（清算表 `status`，页面「账务状态」）**

| 值 | 含义 | 补处理含义 |
|----|------|------------|
| 0 | 未入账 | — |
| 2 | 已入账 / 完成 | 强制成功后的目标态之一 |
| 5 | 入账失败 | 强制失败后的目标态 |
| 6 | 未处理 | 差错导入后默认可补处理状态（参数 `SQUARE_ERR_REDEAL=1`） |
| 7 | 补处理成功 | 正常补处理成功 |
| 8 | 超时未知 | 可「结果同步」或强制成功/失败 |
| 9 | 已挂账 | 入挂账账号成功 |
| Z | 补处理处理中 | 联机加锁中 |

**补处理状态 `K_CCCLZT`（差错表 `reserve1`）**

| 值 | 含义 | 说明 |
|----|------|------|
| 空 / 0 | 否（未处理） | 导入初值一般为 `0` |
| 1 | 是（已成功） | 补处理 / 强制成功后 |
| 2 | 处理中 | 发起补处理时加锁；前端隐藏「补处理」按钮 |
| P | 待审批 | 换户需审批时（部分银行字典） |

基线字典仅 `0-否 / 1-是`；`2-处理中`、`P-待审批` 由增量 / 银行脚本补充。页面展示时空值按 `0` 翻译。

## 4. 功能需求

### 4.1 差错查询（FR-01）

**入口**：资金清算差错记录查询。

**查询条件**

| 条件 | 必填 | 说明 |
|------|------|------|
| 系统流水号 | 否 | `serial_no` |
| 产品代码 | 否 | 分页下拉，支持按 TA 过滤 |
| 开始日期 / 结束日期 | 否 | `square_date` 闭区间；前端限制结束日不早于开始日 |
| 客户标识类型 + 客户标识 | 互为条件必填 | 类型有值则标识必填，反之亦然；类型=证件时证件类型必填 |
| 客户类型 | 条件显示 | 参数 `LIMIT_PER_ORG_QUERY_CONDITION=1` 时显示；个人/机构柜员只读且默认本柜员类型 |

**列表字段（业务关注）**

入账日期、客户编号/名称、银行账号、产品代码/名称、清算金额、失败原因/编码、币种、流水号、清算序号、主机流水号、备注（`reserve2`）、处理日期、业务代码、购买渠道、交易机构、开户机构、摘要、补处理状态、账务状态、账务方向。

**查询规则**

1. 主查 `tbdxfundsquareerr`；清算侧字段（账务方向、账务状态、主机流水、渠道、机构等）在结果格式化时按内部客户号关联分片清算表。
2. 多法人柜员按 `bank_no` 过滤；部门产品权限过滤 `prd_code`。
3. 个人/机构查询隔离（配置 `isEnablePerOrgQry=true`）：未指定客户时 exists 关联 `tbclientmap.client_type`。
4. 支持下载（同查询 SQL + Excel 模板）。

### 4.2 单笔补处理（FR-02）★ 核心

**前置条件**

- 有 Deal 权限；
- `reserve1 ≠ 1`（未成功）、`reserve1 ≠ 2`（非处理中）；
- `batch_status` 不为 `Z` / `8` / `2`（处理中 / 超时 / 已完成时前端隐藏补处理）；
- 内部客户号非空（空则视为内部户，标准不走 110500，见 FR-07）；
- 资金账号非空；清算序号非空；
- 账务状态在参数 `DEAL_SQUARE_STATUS` 允许范围内（默认 `6`）；
- 业务代码、账务方向若配置了白名单（`DEAL_SQUARE_BUSIN_CODES` / `DEAL_SQUARE_LIQU_DIRS`），必须命中。

**操作**

1. 若参数 `REDEAL_CHANGE_BANK_ACC=1`：弹出补处理窗，允许修改银行账号后提交。
2. 否则确认框：「确认线下未处理过该账务，是否发起补处理？」
3. 系统发联机 110500 → 核心 300404 重新入账。
4. 成功：差错 `reserve1=1`，`reserve2=补处理成功`；清算 `status=7`（补处理成功），`batch_status=2`。
5. 失败：差错 `reserve1` 回 `0`，`err_msg` 记核心错误；清算按失败/超时解锁。
6. 超时：清算 `status=8`，柜员可用「结果同步」查证。

**换卡**：参数 `REDEAL_CHANGE_BANKACC=1` 且上送新卡号时，发核心使用新账号，成功后写入 `new_bank_acc`。

### 4.3 强制成功（FR-03）

**场景**：线下已入账成功，系统侧仍为差错/超时，不再发核心。

**规则**

- 确认：「是否发起强制成功？」
- `forceFlag=0`，110500 **不发核心**，本地置成功。
- 允许原账务状态含超时 `8`（在默认可处理状态上追加）。
- 清算 `status=2`（已入账），`err_msg` 追加「|强制处理为成功」；差错 `reserve1=1`，`reserve2=强制处理成功`。
- `batch_status=2` 时前端隐藏该按钮。

### 4.4 强制失败（FR-04）

**场景**：确认无法入账、或线下已按失败处理。

**规则**

- 确认：「是否发起强制失败？」
- `forceFlag=1`，不发核心。
- 清算 `status=5`（入账失败），`err_msg` 追加「|强制处理为失败」；差错 `reserve1=0`，`reserve2=强制处理失败`。
- 同样允许超时记录强制失败。

### 4.5 入挂账账号（FR-05）

**场景**：客户账无法入，资金入产品挂账账号。

**显示条件**（同时满足）

- 有 `ifmCCxglDxfundSqaureErrOtherDeal` 权限；
- `liqu_dir=1`（上账）；
- `reserve1 ≠ 1`。

**规则**

- 前端组装 `addForPrdGzAccount=1`，`forceFlag=2`（2 不上送 ForceFlag，避免被当成强制处理）。
- 核心入账账号改为参数 `PrdGzAccount`。
- 成功：清算 `status=9`（已挂账）；差错 `reserve2=入挂账账号成功`。

### 4.6 结果同步（FR-06）

**场景**：补处理发核心超时（`status=8`），需向核心查证真实结果。

**规则**

- 仅 `status=8` 显示并允许操作。
- 发核心查证接口 **300606**。
- 核心返回成功：清算 `status=7`，`batch_status=2`。
- 核心返回失败：清算 `status=6`，`batch_status=5`，并刷新 `old_square_no`。
- 当前实现**不回写**差错表 `reserve1`（相关 SQL 已注释）。

### 4.7 内部户补处理（FR-07）

内部客户号为空的差错（内部户、批量导入允许空客户号）：

- 参数 `SQAURE_ERR_NO_CLIENTINFO_MODE=1` 时查询仍可展示并回填清算信息；
- 参数 `EMPTY_INCLIENTNO_REDEAL=1` 时允许补处理；
- 管理台**直调 300404**，不经 110500；
- 强制成功/失败在管理台本地改表。

标准校验：内部客户号为空时提示「可能为内部户，不支持补处理」。

### 4.8 文件模式补处理（FR-08）★

适用于**核心以文件接口收补处理入账、回盘差错文件**的银行（与联机 110500/300404 互为通道，按行内核心能力二选一为主；部分个性化 Vue 文案为「生成补处理文件并发送核心」）。标准管理台挂两个按钮并配子交易权限；文件生成/合并/取回盘的具体 Bean 多为银行个性化（如广农商 `guangznsh`）。

#### 4.8.1 业务目标

| 目标 | 说明 |
|------|------|
| 批量送账 | 柜员勾选多笔未成功差错，一次生成补处理入账文件送核心，避免逐笔联机 |
| 可追踪批次 | 每一批发送有独立批次流水（`file_serial_no` / MethodTrack.reserve1），可与主机文件、回盘对应 |
| 取回盘闭环 | 核心处理完成后取补处理结果文件，成功/失败分别回写差错表与清算表 |
| 防重防并发 | 同批未完成禁止再发；已发送未取结果禁止再发；调度节点执行中禁止重入 |

#### 4.8.2 操作步骤（两步必须按序）

| 步骤 | 按钮 / 子交易 | 调度作业 | 业务动作 |
|------|---------------|----------|----------|
| 1 | 勾选记录 → **生成发送补处理**（`ifmCQsglSquareErrPostFileByCond`） | **J210713** | 加锁 → 登记批次 → 各片区生成补处理文件 → 公共合并送核心 → 标记「已发送待取结果」 |
| 2 | **获取补处理结果**（`ifmCQsglSquareErrGetFileByCond`） | **J210813** | 校验已发送 → 取核心回盘 → 成功置补处理成功、失败还原可再补 → 回写清算状态 |

两步均为**异步调度**：管理台提交后立即返回，实际处理看批量节点日志 / MethodTrack / 差错表状态。柜员应在发送成功后再点取结果，取结果完成前勿对同批记录再发。

#### 4.8.3 前置与校验（发送）

1. 有 PostFile 权限；**必须勾选**至少一条差错（未勾选提示先选择数据）。
2. 所选记录差错表 `reserve1` **不能为** `1`（已成功）或 `2`（处理中）；否则提示「状态不允许补处理」或「正在处理中」。
3. MethodTrack（当日、`RepairSquare` / `remedyPostFileByCond`）：
   - 状态为 **处理中（DOING）** 且已有批次流水 → 「有数据正在处理,请等待处理完成」；
   - 状态为 **已发送（WITHDRAW）** → 「数据已发送完成，请先获取结果」（禁止未取结果再发）；
   - 调度 `J210713` 节点正在执行 → 「节点正在执行中...」。
4. 发送链公共侧还会校验：对应清算流水账务状态须为**未处理（`status=6`）**；同日同批或所选流水已存在 `tbhostfile`（trans_code=210713）则禁止重复生成。
5. 上送内容：勾选流水号列表 `SerialNos`、内部客户号列表 `InClientNos`（与流水一一对应），以及当前查询条件（产品、日期、客户标识等，供调度透传）。

#### 4.8.4 前置与校验（取结果）

1. 有 GetFile 权限；**不强制勾选**（按 MethodTrack 上一批次流水取回盘）。
2. MethodTrack 必须已是 **WITHDRAW（账务已成功发送核心）**，否则提示「账务未成功发送核心,请先发送账务给核心」。
3. 调度 `J210813` 节点不能正在执行。
4. 核心侧须已产生对应补处理结果文件（文件名与发送批次流水、系统日期、TA 编码约定一致，见 4.8.6）；取不到文件则本批失败，可排查后再取或按银行规则重发。

#### 4.8.5 状态与数据回写（业务口径）

**批次控制（MethodTrack，非差错表字段）**

| deal_status | 含义 | 允许操作 |
|-------------|------|----------|
| 空 / 失败（FAIL） | 可发起新发送 | 生成发送 |
| 处理中（DOING） | 发送链执行中 | 等待 |
| 已发送（WITHDRAW） | 文件已送核心，待取回盘 | 仅允许获取结果 |
| 成功（SUCC） | 本轮取结果完成 | 可再勾选未成功记录发起新批 |

管理台在发起发送时写入新的批次流水到 MethodTrack.`reserve1`；该流水同时写入差错表 `file_serial_no`，用于回盘匹配。

**差错表 `tbdxfundsquareerr`**

| 时机 | reserve1 | file_serial_no | reserve2 / 其它 |
|------|----------|----------------|-----------------|
| 发送链登记批次（公共 211713） | `0`→`2`（处理中） | — | — |
| 片区/公共写批次号 | 保持处理中 | = 本批 MethodTrack 流水 | — |
| 回盘中出现在失败文件 | →`0` | 失败行随后清空为空格 | 记 `err_msg`/`err_code`、操作柜员 |
| 同批未出现在失败文件（视为成功） | →`1` | 保留批次号 | `reserve2=补处理成功`，`reserve3=操作柜员` |

**清算表 `tbdxfundsquare` / `tbdxfundhissquare`（与联机补处理目标态对齐）**

| 时机 | 典型结果 |
|------|----------|
| 片区生成文件时加锁 | `status`/`batch_status` 置处理中（如 `Z`），防止并发补处理 |
| 回盘成功（差错 reserve1=1） | `status=7`（补处理成功），`batch_status` 对齐完成 |
| 回盘失败（差错 reserve1=0） | `status=6`（未处理，可再补）或 `5`（入账失败），由参数 `SQUARE_ERR_REDEAL` 决定，与日启差错导入口径一致 |

#### 4.8.6 文件约定（标准命名）

参数 `HOST_FILE_NAME_MODE=1` 时文件名中插入 `.6.0.` 段。

| 方向 | 标准文件名模式 | 说明 |
|------|----------------|------|
| 送核心（补处理入账） | `squarerepair[.6.0].{taCode}.{批次流水}.{系统日期}` | 各交易片区先出分片文件，公共合并后送主机；银行可再映射为行内主机文件名（如广农商 `xzhlc_qs.156.{日期}.{批次}`） |
| 核心回盘（补处理差错） | `bkerrsquarerepair[.6.0].{taCode}.{批次流水}.{系统日期}` | 仅含**失败**明细；同批未出现在该文件中的记录按成功处理（与日启 `bkerrsquare`「有则失败」口径一致） |

回盘标准列语义与日启主机差错文件对齐（流水号、失败原因、错误码等）；公共导入后可按内部客户号拆片区文件，供交易片区回写清算。

#### 4.8.7 挂账与个性化

- **入挂账**：文件模式不走管理台「入挂账账号」按钮；部分银行在生成补处理文件时，若差错 `err_code=3`（约定挂账类失败码），则文件中账号替换为参数 `PrdGzAccount`（产品挂账账号）。未配置挂账号则生成失败。
- **个性化**：创建文件 Bean（`T210713_CreateRepairSquareFile`）、合并送核心（`T210713_MergeSquareFileService`）、取回盘（`T210813_GetHostFileService`）按银行 Spring 装配；无个性化 Bean 时公共/交易适配器走通用骨架，字段格式与主机交互以该行为准。
- **与联机模式关系**：同一笔差错不应在文件批处理未结束时再点联机补处理（`reserve1=2` / 清算处理中会拦截）。业务上按行内规范固定一种主通道，避免双通道重复入账。

#### 4.8.8 约束摘要

- 未勾选不可发送；已成功 / 处理中不可入选发送。
- 发送与取结果**严格串行**：先发后取；取完（或失败复位）前禁止再发。
- 批次以 MethodTrack + `file_serial_no` 关联，跨日以系统日期（initDate）隔离。
- 异步失败时 MethodTrack 置 FAIL，允许排查后重新发送（须确认核心侧未重复入账）。

### 4.9 预览与下载（FR-09）

- 行内「预览」：明细弹窗，展示全部列。
- 工具栏下载：按当前查询条件导出。

## 6. 数据来源（业务口径）

差错行从何而来，决定柜员何时能在管理台看到数据：

| 来源 | 时机 | 柜员可见条件 |
|------|------|----------------|
| 日启取主机差错 T210213 | 主机回盘 `bkerrsquare` | 公共导入 → 拆片区 → 交易导入回写清算状态 → T211213 再同步公共；管理台查公共库，需跑完同步 |
| 日间轮询差错 T210314 | 日间分批入账回盘 | `is_daily=1`，与日启差错隔离，互不覆盖删除 |
| 联机/批量入账失败 | T210013 等直连核心失败 | 交易片区 INSERT + API 同步公共，当日即可查 |
| 组合宝对账不平 | Task210455 | `reserve4='yeb'`，走江南盈菜单 |
| 银行个性化 | 反洗钱、定期定额等 | 以该行节点为准 |

导入后清算状态：

- 参数 `SQUARE_ERR_REDEAL=1`：清算 `status=6`（未处理，可补处理）；
- 否则：`status=5`（入账失败）。

## 8. 业务规则摘要

1. **一笔差错只能成功补处理一次**：`reserve1=1` 后补处理按钮隐藏。
2. **处理中不可重入**：`reserve1=2` 或清算 `batch_status=Z`。
3. **强制处理不发核心**：依赖柜员确认线下结果，存在操作风险，需权限与双人复核（银行可开审批）。
4. **超时优先查证再强制**：结果同步走 300606；强制成功仅在确认核心已入账后使用。
5. **上账才允许入挂账**：`liqu_dir=1`。
6. **内部户与普通客户路径分离**：普通客户 110500；内部户直调 300404。
7. **文件模式与联机模式按行内能力选用**：文件模式用 MethodTrack（`RepairSquare`/`remedyPostFileByCond`）串行控制「发送→取结果」；已发送未取结果禁止再发；处理中记录勿再点联机补处理，避免双入账。
8. **文件回盘「有则失败」**：补处理结果文件只列失败明细；同批 `file_serial_no` 未出现在失败文件中的记录视为补处理成功。

## 9. 验收要点

| 场景 | 期望 |
|------|------|
| 日启导入差错后查询 | 能按日期查到失败原因，账务状态为 6（或 5） |
| 正常补处理成功 | 核心入账成功；差错 reserve1=1；清算 status=7 |
| 核心明确失败 | 差错 reserve1 回 0；可再次补处理 |
| 核心超时 | 清算 status=8；可结果同步；可强制成功/失败 |
| 换卡补处理 | 参数开启后弹窗改账号，成功写入 new_bank_acc |
| 入挂账 | 仅上账方向显示；成功 status=9 |
| 文件模式-发送 | 勾选未成功记录；J210713 异步完成；reserve1=2、file_serial_no 有值；MethodTrack=WITHDRAW；核心收到补处理文件 |
| 文件模式-取结果（全成功） | 回盘无失败行；所选差错 reserve1=1、reserve2=补处理成功；清算 status=7；MethodTrack=SUCC |
| 文件模式-取结果（部分失败） | 失败行 reserve1=0 可再补、file_serial_no 清空；成功行 reserve1=1；清算按成功/失败分别回写 |
| 文件模式-防重 | 处理中再发被拦；已发送未取结果再发提示先获取结果；清算非未处理状态禁止生成 |
| 无权限 | 对应按钮不显示 |
| 处理中记录 | 补处理按钮隐藏，再次提交报「正在处理中」 |
