# T100002 解约流程详解（入口：T100002HSAdapter）

## 1. 文档范围
- 入口类：`T100002HSAdapter`
- 入口文件：`app/lcpt-server/sale/lcpt-pub/lcpt-pub-common/lcpt-pub-online-adapter/src/main/java/com/hundsun/lcpt/pub/online/adapter/T100002/T100002HSAdapter.java`
- 目标：梳理“客户解约（100002）”完整处理链路，明确：
  - 流程步骤
  - 操作到的数据库表
  - 参数开关与控制逻辑
  - 分业务解约与全量解约的差异
  - **解约如何联动各子系统自动销户**（见第 10 节）
  - **解约如何支持银行卡解登记**（见第 11 节；分业务 vs 全量差异见 **11.10**）

## 1.1 关键字典语义（来自 `IDict`）
- 签约状态 `K_QYZT`
  - `QYZT_NORMAL=0`：正常
  - `QYZT_SINGOFF=1`：解约
  - `QYZT_CHANGE=2`：换卡
- 账户状态 `K_ZHZT`（理财账户/资产账户常用）
  - `ZHZT_PRE_CLOSE=5`：预销户
  - `ZHZT_CLOSE=X`：销户
- 产品类型 `K_CPLX`（100002 常见）
  - `0` 基金（`CPLX_FUND`）
  - `1` 理财产品（`CPLX_FINA`）
  - `2` QDII（`CPLX_QDII`）
  - `3` 贵金属（`CPLX_METAL`）
  - `4` 银保（`CPLX_INSURE`）
  - `5` 积存金（`CPLX_GOLD`）
  - `8` 信托产品（`CPLX_TRUST`）
  - `A` 大额存单（`CPLX_DECD`）
  - `B` 资管计划产品（`CPLX_ZGJH`）
  - `E` 结构性存款模板（`CPLX_JGXCK`）
  - `X` 商业养老金（`CPLX_COMMERCIALPENSION`）

## 2. 总体流程（主干）

`action()` 主流程：
1. `transRequest`：请求字段校验、基础上下文装配
2. 判断是否走分业务解约 `signOffByPrdType`
3. 预校验：
   - 分业务：`checkDataByPrdType`（按 `PrdTypes` 逐个业务校验）
   - 非分业务：`checkData`
4. `toLocalFirst`：先落交易流水 `tbaccreq*`
5. 发外围系统：
   - 非分业务可能发组合中心 `toHstc`
   - 发核心/主机 `toHost`
   - 发 ECIF `toEcif`（参数控制）
6. 本地落地：
   - 分业务：`toLocalByPrdType`（主要更新产品标识）
   - 非分业务：`toLocal`（完整解约状态落地）
7. `packAnswer` 组装应答

## 3. 两类流程分支

## 3.1 全量解约（非分业务）
- 关键方法：`checkData -> toLocalFirst -> toHstc(可选) -> toHost -> toEcif(可选) -> toLocal`
- 特点：
  - 客户级别状态会更新为解约
  - 银行账号可能做自动解登记（发 100014/100814）
  - 可触发自动销户（基金/信托/资管/结构性存款/商养等子系统）

## 3.2 分业务解约
- 触发条件：`SIGN_BY_PRDTYPES` 已配置，且请求上送 `PrdTypes`，并且“客户当前签约业务数 > 本次解约业务数”
- 关键方法：`checkDataByPrdType -> toLocalFirst -> toHost(可能跳过) -> toEcif(可选) -> toLocalByPrdType`
- 特点：
  - 只剔除对应业务类型标记，不一定把客户整体置为解约
  - 银行账号 `prd_types` 会同步剔除
  - 当某张卡剔除后 `prd_types=' '` 时，卡状态更新为解约

## 4. 详细步骤说明

## 4.1 请求转换与基础校验（`transRequest`）
- 必输：`AccType`、`Account`
- 若请求 `SignOffFlag != N`，会强制置为 `Y`（作为自动销户参与标志）
- 设置统一签约模式标记：`MUTI_BANK_ONLY_SING_ONE`

## 4.2 分业务判断（`signOffByPrdType`）
- 读取 `SIGN_BY_PRDTYPES` 决定是否启用分业务模式
- 校验请求 `PrdTypes` 合法性（是否存在于 `K_CPLX` 字典）
- 若上送 `BankAcc`，会校验该卡是否包含请求业务类型（卡维度 `prd_types`）
- 若请求业务不是客户已签约业务，报错
- 若“不是最后一个业务”则置 `transVar.signOffByPrdType=true`

## 4.3 非分业务主校验（`checkData`）
核心校验点：
- 客户状态校验：已解约直接报错
- 日终/BTA 禁止交易校验（`DAILY_END_FORBIDDEN_TRANS`、`BTA_FORBIDDEN_TRANS` 等）
- 自动销户路径校验（`AutoCloseAcc`、`AUTO_CLOSE_PRD_TYPES`）
- 在途异步换卡限制：`T100002_CHECK_ONWAY_ASYNC_CHGCARD`
- 预校验/解登记前置（`isPreCheck100002`、`CHECK_TRANSFER_SWITCH`）
- 自动解登记（`SIGNOFF_BANKACC`）调用 `T100014HSAdapter/T1L0014HSAdapter/T100814HSAdapter`
- 可选发大额存单校验（`SIGNOFF_CHK_DECD`）与积存金校验（`SIGNOFF_CHK_GOLD`）

## 4.4 分业务校验（`checkDataByPrdType`）
按每个 `prdType` 分别执行：
- 基金/理财/QDII/信托/资管/商养等资产账户状态校验（重点判断是否仍存在 `acc_status` 不为 `ZHZT_CLOSE(X)`，或不在 `ZHZT_PRE_CLOSE(5)`、`ZHZT_CLOSE(X)` 范围内的记录）
- 根据参数决定是否自动发子系统销户交易
- 贵金属、银保、黄金二级代理等专门校验
- 合约信息通知条件判断（`IS_SEND_ARINFO`）

## 4.5 本地流水预落地（`toLocalFirst`）
- 先生成序列号与 `AccReq`
- 写入交易流水（`AccReqService.addAccReq`）
- 作用：先有流水，再发外围系统，便于失败回写

## 4.6 发核心（`toHost`）
- 关键跳过条件：
  - 已标记发组合中心
  - 分业务且参数 `TO_HOST_100002=Y`（分业务解约不发核心）
  - 请求 `IsPrd=Y` 或 `NotToHost=Y`
  - 参数 `SIGN_SEND_300905=Y`（不发 300905）
- 正常时组包 `R300905Dataset` 并发送
- 成功回填 `hostSerial`、`contrId`

## 4.7 发 ECIF（`toEcif`）
- 开关：`JNNS_SEND_ECIF_FLAG` 或 `T100002_SEND_ECIF_FLAG`
- 可配置交易码：`T100002_TOECIF_TRANSCODE`
- 支持参数 `T100002_SEND_HOST_USE_PUB` 控制使用公共接口方式
- 超时按成功处理（仅超时场景）

## 4.8 本地落地（全量）`toLocal`
- 更新 `tbclientseller*` 为解约状态（含 `prd_type_msg_flag` 清空）
- 根据多法人参数决定是否更新 `tbclient*` 为解约
- 成功更新 `tbaccreq*` 状态为成功
- 根据参数删除 `tbtransaccount*`
- 根据参数更新 `tbbankacc*` 为解约/签解约日期/清空 `prd_types`
- 根据参数更新 `tbclientriskinfo*` 风险字段
- 双核心场景更新 `tbclientnomap2`
- 根据参数更新反洗钱状态（`tbclientaml*`）

## 4.9 本地落地（分业务）`toLocalByPrdType`
- 从 `clientSeller.prdTypes` 与 `prdTypeMsgFlag` 中剔除本次业务
- 更新 `tbclient*` 与 `tbclientseller*`
- 更新 `tbaccreq*`（摘要写“本次解约业务[...]”）
- 可删除 `tbtransaccount*`（仅当剔除后已无业务）
- 更新 `tbbankacc*`：
  - 先更新 `prd_types`
  - 若 `prd_types=' '` 则更新卡状态为解约
- 支持“分业务解约不送卡”场景：对客户下所有卡批量剔除

## 5. 涉及数据库表清单（按职责）

## 5.1 客户与签约主数据
- `tbclient*`：客户基本状态（签约状态字段，常见 `0=正常`/`1=解约`）与最近修改时间
- `tbclientseller*`：客户在机构/法人维度签约状态（`K_QYZT`）、产品标记、短信标记
- `tbbankacc*`：银行卡签约状态（`K_QYZT`）、签约产品标记、签解约日期
- `tbtransaccount*`：交易介质映射，解约可删除
- `tbclientmap`：ECIF/核心补卡号时兜底查询
- `tbclientnomap2`：双核心客户号映射状态同步

## 5.2 交易流水与扩展
- `tbaccreq*`（通过 `AccReqService`）：解约交易主流水
- `tbaccreqext*`（通过 `AccReqExtService`）：扩展信息（全局流水号等）

## 5.3 资产账户/TA 相关
- `tbassetacc*`：核心校验与自动销户判断主表（按产品类型）；100002 解约核心判断是该客户在目标业务下是否仍存在“未销户账户”（即 `acc_status != ZHZT_CLOSE(X)`，部分分支要求进一步达到 `acc_status in [ZHZT_PRE_CLOSE(5), ZHZT_CLOSE(X)]`）
- `tbtainfo`：TA 状态、公私募属性校验

## 5.4 银行卡解登记与虚拟卡
- `tbvirbankaccmap`：解登记时过滤虚拟卡
- `tbmsgnoticesync`：在途换卡异步消息校验

## 5.5 组合中心/组合签约
- `tbgrpbankmap`：组合虚拟卡映射
- `tbclientgrpsign*`：组合签约关系（可控制是否按此发组合中心）

## 5.6 风险与反洗钱
- `tbclientriskinfo*`：风险等级清零/重置
- `tbclientaml*`（经 `ClientAmlDao`）：反洗钱状态更新

## 5.7 业务在途/限制校验表
- 贵金属：`tbmetalreq`、`tbmetalautoinvest`、`tbmsharedetail`
- 银保：`tbshareinsure`、`tbinsurereq`
- 黄金二级代理：`tbgoldacc`、`tbgoldsign`
- 大额存单扩展校验：`tbinstext`

## 6. 参数控制逻辑总表（重点）

以下为 100002 解约流程中出现频率高、影响主路径的参数：

- `SIGN_BY_PRDTYPES`
  - 含义：启用分业务签解约模式
  - 影响：决定是否走 `signOffByPrdType` 分支

- `TO_HOST_100002`
  - 含义：分业务模式下是否不发核心（注释语义）
  - 影响：`toHost` 早退

- `SIGN_SEND_300905`
  - 含义：是否发送 300905（解约发核心交易）
  - 影响：为 `Y` 时不发 300905

- `T100002_SEND_ECIF_FLAG` / `JNNS_SEND_ECIF_FLAG`
  - 含义：是否发 ECIF
  - 影响：调用 `toEcif`

- `T100002_TOECIF_TRANSCODE`
  - 含义：ECIF 交易码覆盖
  - 影响：`toEcif` functionId 由参数替换

- `T100002_SEND_HOST_USE_PUB`
  - 含义：发 ECIF/核心是否走公共接口
  - 影响：选择 `IHostService.execute300002` 或 `HostServiceClient`

- `T100002_TOHOST_BANKACC`
  - 含义：发核心是否强制带 `BankAcc`
  - 影响：`setBankAcc` 是否执行兜底取卡

- `AutoCloseAcc`
  - 含义：是否启用自动销户总开关
  - 影响：自动销户前置校验与实际发起

- `AUTO_CLOSE_PRD_TYPES`
  - 含义：可自动销户产品类型集合
  - 影响：`checkData` 中 `tbassetacc*` 条件

- `IS_FUND_AUTO_CLOSE_ACC` / `IS_FINA_AUTO_CLOSE_ACC` / `IS_ASSET_AUTO_CLOSE_ACC` / `IS_DXCP_AUTO_CLOSE_ACC`
  - 含义：基金/理财/资管/商养分产品自动销户开关
  - 影响：`checkDataByPrdType`、`checkAutoCloseAssetAccByPrdType` 的自动销户路径

- `CLIENT_OFF_ENTER_APP`
  - 含义：多子系统自动销户入口系统标识
  - 影响：决定调本地 Bean 还是跨子系统远程发送

- `CHECK_TRANSFER_SWITCH`
  - 含义：是否启用取消登记校验与转发检查
  - 影响：100014 预校验 + transfer 通知链路

- `SIGNOFF_BANKACC`
  - 含义：客户解约时是否自动发银行卡解登记
  - 影响：批量发 100014/100814

- `T100002_SIGNOFF_100814`
  - 含义：是否改用 100814 取消登记
  - 影响：`pack100014Dataset` 中交易码切换

- `TERMINATE_TO_UNREGISTER_FILTER_VIRBANK`
  - 含义：取消登记时是否过滤虚拟卡
  - 影响：`not exists tbvirbankaccmap` 条件拼接

- `T100002_CHECK_ONWAY_ASYNC_CHGCARD`
  - 含义：是否校验在途换卡
  - 影响：存在未完成换卡时拒绝解约

- `DELCLIENTBANKACC`
  - 含义：是否删除/保留银行账号关系
  - 影响：`toLocal` 中是否更新 `tbbankacc*`

- `TRANSACCOUNT_DEL`
  - 含义：解约是否删除 `tbtransaccount*`
  - 影响：全量/分业务本地落地的删除动作

- `APPROP_RISK_PRDTYPE`
  - 含义：解约后是否重置客户风险信息
  - 影响：更新 `tbclientriskinfo*`

- `IS_CHECK_TWO_HOST_100001`
  - 含义：双核心模式下是否同步客户号映射状态
  - 影响：更新 `tbclientnomap2`

- `T100002_MODIFY_CLIENTAML_STATUS`
  - 含义：解约是否重置客户反洗钱状态
  - 影响：更新 `tbclientaml*`

- `IS_SEND_ARINFO`
  - 含义：是否发送合约管理信息
  - 影响：触发 `SendARInfoService.SignoffSendARInfo`

- `T100002_MUTI_BANK_SIGN_OFF`
  - 含义：多法人模式下是否仅最后一行解约时更新客户主状态
  - 影响：控制 `tbclient*` 状态更新时机

- `T100002_UPT_MODIFY_DATE`
  - 含义：是否更新客户最近修改日期
  - 影响：更新 `last_modify_date/modi_time`

- `SIGNOFF_CHK_DECD` / `SIGNOFF_CHK_GOLD`
  - 含义：是否发大额存单/积存金解约校验
  - 影响：调用 `checkSendDecd/checkSendGold`

## 8. 常见失败点（排障优先顺序）
- 参数缺失：`AccType`/`Account`/分业务缺少 `PrdTypes`
- 客户已解约或状态异常
- `tbassetacc*` 账户状态未达到解约要求：仍存在 `acc_status != ZHZT_CLOSE(X)`，或（在需要预销户收敛的分支）仍存在不在 `ZHZT_PRE_CLOSE(5)`、`ZHZT_CLOSE(X)` 范围内的记录（常见原因是自动销户参数未对齐）
- 在途换卡（`tbmsgnoticesync`）
- 银行账号取消登记失败（100014/100814）
- 子系统自动销户服务 Bean 未配置（`NoSuchBeanDefinitionException`）
- ECIF/主机返回非成功（ECIF 超时除外）

## 9. 结论
- `T100002` 是“先流水、后外围、再本地落地”的典型强一致交易编排。
- 实际行为高度依赖参数，尤其是：
  - 分业务开关
  - 自动销户开关族
  - 是否发核心/ECIF/取消登记
- 排查解约问题时，建议先确认 `PrdTypes + 参数快照 + tbassetacc*.acc_status（按 K_ZHZT 翻译）+ tbaccreq*流水` 四要素。

## 10. 解约如何支持自动销户（专题）

> 问题：`T100002HSAdapter` 如何支持「解约时自动销户」？  
> 答案要点：**双闸门（参数 + 上送字段）→ 查 `tbassetacc*` → 按产品类型转发各子系统销户交易（先校验再正式）→ 回验预销户/销户状态 → 落库打标**。  
> 发生时机：在 `checkData` / `checkDataByPrdType` 阶段（`toLocalFirst` 写解约流水之前），不是本地落地之后。

### 10.1 总开关与请求字段（双闸门）

| 控制点 | 位置 | 规则 |
|---|---|---|
| 系统参数 `AutoCloseAcc` | `checkData` / `checkDataByPrdType` | `Y` 才走自动销户；代码取值默认缺省为 `N`（参数未配置则关闭） |
| 请求字段 `SignOffFlag` | `transRequest` | 若上送值 **不是** `0`，强制改为 `1`；只有显式上送 `0` 才关闭「本次请求参与自动销户」 |
| 组合条件（全量解约） | `checkData` | **`AutoCloseAcc=Y` 且 `SignOffFlag=Y`** 才进入自动销户分支；否则走「不允许存在未销户资产账户」的硬校验 |

含义：
- 银行侧要开自动销户：先配 `AutoCloseAcc=1`。
- 渠道若不想本次自动销户：必须上送 `SignOffFlag=0`（不送或送其它非 0 值都会被置为 1）。
- 关闭自动销户时：客户名下凡 `tbassetacc*.acc_status != ZHZT_CLOSE(X)` 一律拒绝解约。

### 10.2 全量解约路径（`checkData`，非分业务）

开启双闸门后，逻辑分四步：

**① 非自动销户业务先挡死**

- 读取 `AUTO_CLOSE_PRD_TYPES`（默认约 `2~8`，即 QDII、信托等，以参数为准，`~` 分隔）。
- 若存在 `prd_type **不在** AUTO_CLOSE_PRD_TYPES` 且 `acc_status != 销户(X)` 的账户 → 报错（「除 QDII/信托/基金 TA 外还有未销户账户」类提示）。
- 即：只有「允许自动销户」的产品类型才会被代发销户；其它类型必须事先已销户。

**② 选出待销户资产账户**

```text
select ta_code, prd_type from tbassetacc{分表}
 where in_client_no=?
   and acc_status not in (预销户5, 销户X)
   and prd_type in (AUTO_CLOSE_PRD_TYPES)
   and bank_no=当前法人行
```

- 已是预销户(5)/销户(X) 的 **不再发起** 销户交易（「标准化预销户状态不发起销户」）。
- 若查出有待销户记录，则必须配置公共参数 `CLIENT_OFF_ENTER_APP`（解约入口子系统）；否则报「包含多子系统的解约自动销户，需要配置入口的子系统」。

**③ 两遍调用 `splitSendAllPrdtypes`（先校验、再正式）**

| 遍次 | `CheckFlag` | 说明 |
|---|---|---|
| 第一遍 | `1` | 仅校验各子系统是否允许销户 |
| 第二遍 | `0` | 正式发起销户（**预校验 `isPreCheck100002=true` 时跳过本遍**，见 T202604165063） |

合并 TA（`T100002_MERGE_FUND_ASSET` + TA 级 `MERGE_FUND_ASSET`）时：基金与资管会交叉再校验一遍对方产品类型。

**④ 销户后回验 + 打标**

- 再次统计：`AUTO_CLOSE_PRD_TYPES` 下是否仍存在非预销户/非销户账户；有则失败。
- 成功则 `transVar.setSignoffFlag(true)`，后续：
  - `toLocalFirst`：`tbaccreq.control_flag` 第 11 位（下标 10）置 `'1'`；
  - `toLocal`：`tbclientseller.signoff_flag` 置 `Y`。

### 10.3 分发到各子系统销户交易（`splitSendAllPrdtypes`）

按 `prd_type` 组包并下发（入口子系统 = `CLIENT_OFF_ENTER_APP` 时调本地 Bean，否则 `OnlineServiceClient` 远程）：

| prd_type | 销户交易码 | 组包方法 | 本地 Bean / 远程类型 |
|---|---|---|---|
| `0` 基金 | `110101` | `pack110101Dataset` | `T110101HSAdapter` / `DXFUND_PUB` |
| `B` 资管 | `1B0101`（商养控制位可切 `1B5101`） | `pack1B0101Dataset` | `T1B0101`/`T1B5101` / `DXASSET_PUB` |
| `8` 信托 | `170101` | `pack170101Dataset` | `T170101HSAdapter` / `DXTRUST_PUB` |
| `E` 结构性存款 | `1L0101` | `pack1L0101Dataset` | `T1L0101HSAdapter` / `STRUCT_PUB` |
| `X` 商养 | `1X5101` | `pack1X5101Dataset` | `T1X5101HSAdapter` / `DXCP_PUB` |
| 其它（含理财 `1`） | `100101` | `pack100101Dataset` | `T100101HSAdapter` / `FINA_PUB` |

组包共性：复制解约请求 → 改 `FunctionId`/`TaCode` → `AccType=客户号`、`Account=ClientNo`；可按 `AUTO_TRANS_CHG_CHANNEL` 把渠道改成批量渠道；可带全局流水号（`ADD_GLOBAL_SERIALNO` / `T100002_GEN_GLBALSERIALNO_BY_SYS`）。

找不到对应 Adapter Bean → `自动销户失败，找不到销户服务`。

### 10.4 分业务解约路径（`checkDataByPrdType`）

分业务不是整包走 `splitSendAllPrdtypes`，而是按上送的单个 `prdType` 分支：

1. **基金/理财/QDII/信托（`prdType ∈ "0128"`）**  
   - 总开关仍是 `AutoCloseAcc`。  
   - 另读 `IS_FUND_AUTO_CLOSE_ACC`、`IS_FINA_AUTO_CLOSE_ACC`。  
   - QDII：对未销户账户循环发 `100101`。  
   - 信托：循环发 `170101`（`DXTRUST_PUB`）。  
   - 基金且 `IS_FUND_AUTO_CLOSE_ACC=Y`：对非预销户/非销户发 `110101`。  
   - 理财且 `IS_FINA_AUTO_CLOSE_ACC=Y`：对非预销户/非销户发 `100101`（`FINA_PUB`）。  
   - 未开对应自动销户时：该业务下未销户账户直接拒绝解约。

2. **资管 `B` / 商养 `X`**  
   - 走 `checkAutoCloseAssetAccByPrdType`：  
     - `IS_ASSET_AUTO_CLOSE_ACC=Y` → 资管发 `1B0101`/`1B5101`；  
     - `IS_DXCP_AUTO_CLOSE_ACC=Y` → 商养发 `1X5101`；  
     - 未开则仅校验不得存在未销户账户。

3. 销户后同样要求该 `prd_type` 收敛到预销户(5)或销户(X)。

> 注意：分业务路径对 `SignOffFlag` 的门闩不如全量路径严格（主要看 `AutoCloseAcc` + 分产品开关）；全量路径同时要求 `SignOffFlag=Y`。

### 10.5 与「银行卡解登记 / 预校验」的区别

| 能力 | 是否自动销户 | 说明 |
|---|---|---|
| 自动销户（本节） | 是 | 销的是各子系统 **TA 资产账户**（`tbassetacc*` → 100101/110101/…） |
| `SIGNOFF_BANKACC` 解登记 | 否 | 发 `100014`/`100814`/`1L0014` 取消 **银行卡登记**，见 **第 11 节** |
| `isPreCheck100002` | 半开 | 自动销户只做校验遍（`CheckFlag=1`），**不发正式销户**；解登记也可只做预校验 |

### 10.6 联调/排障检查清单

1. `AutoCloseAcc` 是否为 `1`；请求是否误送 `SignOffFlag=0`。  
2. `AUTO_CLOSE_PRD_TYPES` 是否覆盖当前待销账户的 `prd_type`。  
3. `CLIENT_OFF_ENTER_APP` 是否与发起解约的微服务一致（多子系统必配）。  
4. 对应子系统销户 Bean / 远程是否可达（`NoSuchBeanDefinitionException`）。  
5. 销户后 `tbassetacc*` 是否进入 `5`/`X`；卡死在其它状态会二次报 `ERR_HAVEASSETACC`。  
6. 是否在预校验模式（只校验不销户）。  
7. 分业务时核对 `IS_FUND_AUTO_CLOSE_ACC` / `IS_FINA_AUTO_CLOSE_ACC` / `IS_ASSET_AUTO_CLOSE_ACC` / `IS_DXCP_AUTO_CLOSE_ACC`。

### 10.7 一句话总结

**解约自动销户 = 参数 `AutoCloseAcc`（+ 全量时 `SignOffFlag`）打开后，在校验阶段按 `tbassetacc*` 未销户记录，代发各业务销户交易码（先 `CheckFlag=1` 再 `0`），成功后要求账户进入预销户/销户，并在解约流水与客户签约表上打「解约自动销户」标记；未开启时则要求客户已事先销完所有资产账户才能解约。**

## 11. 解约如何支持银行卡解登记（专题）

> 问题：`T100002HSAdapter` 如何支持「银行卡解登记」？  
> 答案要点：**在全量解约 `checkData` 中，先可选做 100014 预校验，再按 `SIGNOFF_BANKACC` 对客户名下未解约/未换卡的银行卡逐张代发取消登记交易（默认 `100014`，可切 `100814`/`1L0014`），最后强制校验卡状态；本地落地时由 `DELCLIENTBANKACC` 决定是否再改 `tbbankacc*`。**  
> 与第 10 节自动销户的区别：解登记作用对象是 **`tbbankacc*`（银行卡签约）**，不是 `tbassetacc*`（TA 资产账户）。

### 11.1 发生位置与前置闸门

时机：全量解约分支的 **`checkData`**（自动销户逻辑之后、`toLocalFirst` 之前）。分业务 `checkDataByPrdType` **不走**本节的批量解登记主路径（与分业务差异见 **11.10**）。

进入「正式解登记 + 卡状态回验」大段的条件（三者同时满足）：

| 条件 | 含义 |
|---|---|
| `DELCLIENTBANKACC` 为 `Y`（空则代码默认置 `"1"`） | 解约侧要求「卡关系按取消登记处理」；为 `N` 时本段整段跳过 |
| `isPreCheck100002 == false` | 非预校验模式才真正发取消登记 |
| 请求 `CheckFlag != Y` | 上送校验标志为是时不发正式解登记 |

在此之前还有一条**预校验/转发**旁路（可与正式解登记独立开启）：

- 触发：`isPreCheck100002` **或** `CHECK_TRANSFER_SWITCH=Y`
- 动作：对每张候选卡临时改请求 `BankAcc`，调用 `PreCheck100014.check`；并在 `CHECK_TRANSFER_SWITCH=Y` 时 `TransferService.transfer` 通知其它系统
- `PreCheck` 类加载失败则跳过（不报错）

### 11.2 候选银行卡如何选出

正式解登记与预校验共用同类 SQL（统一签约模式用 `distinct(bank_acc)` 且可不带 `bank_no`）：

```text
select bank_acc from tbbankacc{分表}
 where in_client_no=?
   and acc_status != 解约(1)
   and acc_status != 换卡(2)
   [and bank_no=当前法人行]          -- 非统一签约
   [and not exists tbvirbankaccmap] -- TERMINATE_TO_UNREGISTER_FILTER_VIRBANK=Y 时过滤虚拟卡
```

即：只对**仍正常登记**的卡做取消登记；已解约/换卡状态跳过。

### 11.3 正式自动解登记（`SIGNOFF_BANKACC`）

参数注释语义：`1` = 客户解约自动解登记；`0` = 默认不自动解登记。

当 `SIGNOFF_BANKACC=Y` 时：

1. **选 Adapter**
   - 优先本地 Bean `T100014HSAdapter`
   - 若无 100014，且业务类型含结构性存款 `E` 且存在 `T1L0014HSAdapter` → 改用结构性存款取消登记
   - 若 `T100002_SIGNOFF_100814=Y` → 强制改用 `T100814HSAdapter`（银行卡打标/分发取消登记）；Bean 不存在则报「暂不支持解约做分发各个子系统的取消登记」

2. **逐卡组包并执行**  
   - `pack100014Dataset(context, bankAcc, clientNo)`  
   - `adapterBean.execute(requestDataset)`  
   - 成功码：`0000`；或已取消 `ERR_ACCCANCELED`（当作可接受）  
   - 其它错误码直接抛错中断解约  
   - 多卡 `HostSerial` 用逗号拼接回填 `transVar.hostSerial`

3. **未开 `SIGNOFF_BANKACC` 时**  
   - 不代发 100014，但仍受 11.1 闸门约束：若 `DELCLIENTBANKACC=Y`，后面仍会执行「必须已无未取消登记卡」的回验 → 相当于要求渠道/柜面事先做完解登记。

### 11.4 组包规则（`pack100014Dataset`）

| 字段/行为 | 规则 |
|---|---|
| `FunctionId` | 默认 `100014`；`T100002_SIGNOFF_100814=Y` 时改为 `100814` |
| `BankAcc` | 当前循环的待解登记卡号 |
| `AccType`/`Account` | `NeedOriginalInfo=N`（默认）：`AccType=客户号`，`Account=ClientNo`（直销渠道可换 `ChannelClientNo`）；`NeedOriginalInfo=Y`：沿用解约原请求介质 |
| `PwdFlag`/`Passwd` | 个人客户且 `CHECKPWDFLAG=Y` 时验密（密码空则报错）；否则 `PwdFlag=0`；机构不验密 |
| `Channel` | `AUTO_TRANS_CHG_CHANNEL=Y` 时默认改批量渠道；若同时 `CHGCHANNELINTRANS=Y` 则保留原渠道并打 `AutoTransFlag=1` |
| 全局流水 | `ADD_GLOBAL_SERIALNO`；可再开 `T100002_GEN_GLBALSERIALNO_BY_SYS` 由平台重新生成 |
| `OldTransCode` | 固定 `"100002"`，标明由解约触发 |

### 11.5 解登记后强制回验

无论本轮是否真正调用了 100014（只要进入了 11.1 大段），都会再查：

```text
count(*) from tbbankacc* where in_client_no=? and acc_status not in (解约,换卡) [and bank_no=?]
```

`count > 0` → 报错 **「有银行帐号未取消登记」**（`ERR_ACCHAVESIGN`）。

因此典型配置组合：

| `DELCLIENTBANKACC` | `SIGNOFF_BANKACC` | 行为 |
|---|---|---|
| `1` | `1` | 解约内自动发取消登记，并要求全部卡变为解约/换卡 |
| `1` | `0` | 不解约内代发；但回验仍要求卡已取消登记（需事先 100014） |
| `0` | 任意 | 跳过自动解登记与上述回验；由 `toLocal` 直接改卡状态（见下） |

### 11.6 与本地落地 `toLocal` 的衔接

`toLocal` 中更新 `tbbankacc*` 的条件是 **`DELCLIENTBANKACC = N`**（与 checkData 闸门相反）：

- `DELCLIENTBANKACC=0`：`update tbbankacc* set acc_status=解约, signoff_date=交易日, prd_types=' ', modify_date=物理日`（按法人行/统一签约模式拼 WHERE）  
  → **不解约内发 100014，靠本地改状态**。
- `DELCLIENTBANKACC=1`：`toLocal` **不再**改 `tbbankacc*`，期望取消登记交易（或事先解登记）已把卡状态落到解约/换卡。

分业务落地 `toLocalByPrdType` 只剔除卡上 `prd_types`；当剔除后 `prd_types` 为空时才把该卡置解约——那是分业务路径的卡状态收敛，不是本节的批量 100014（详见 **11.10**）。

### 11.7 参数速查

| 参数 | 作用 |
|---|---|
| `DELCLIENTBANKACC` | 是否走「卡必须取消登记」校验段；空默认按 `1`；为 `0` 时改由 `toLocal` 直接改卡状态 |
| `SIGNOFF_BANKACC` | 解约时是否自动代发取消登记 |
| `T100002_SIGNOFF_100814` | 取消登记改发 `100814`（及对应 Adapter） |
| `TERMINATE_TO_UNREGISTER_FILTER_VIRBANK` | 预校验/正式解登记时过滤 `tbvirbankaccmap` 虚拟卡 |
| `CHECK_TRANSFER_SWITCH` | 解约前做 100014 预校验 + 转发通知 |
| `NeedOriginalInfo` | 解登记请求是否沿用解约原 AccType/Account |
| `CHECKPWDFLAG` | 个人客户解登记是否验密 |
| `AUTO_TRANS_CHG_CHANNEL` / `CHGCHANNELINTRANS` | 自动交易渠道改批量或保留原渠道 |
| `ADD_GLOBAL_SERIALNO` / `T100002_GEN_GLBALSERIALNO_BY_SYS` | 全局流水号透传或平台生成 |
| `BIZ_TYPE` 含 `E` | 无 100014 时尝试结构性存款 `1L0014` |

### 11.8 联调/排障检查清单

1. 全量解约还是分业务？分业务不走本节批量 100014。  
2. `DELCLIENTBANKACC` / `SIGNOFF_BANKACC` 组合是否符合预期（见 11.5 表）。  
3. 是否预校验或上送了 `CheckFlag=1`（会跳过正式解登记）。  
4. 本机是否有 `T100014HSAdapter`（或 100814 / 1L0014）。  
5. 虚拟卡是否因 `TERMINATE_TO_UNREGISTER_FILTER_VIRBANK` 被过滤导致「看起来还有卡」/「漏解登记」。  
6. 回验失败「有银行帐号未取消登记」：查 `tbbankacc*.acc_status` 是否仍非 `1/2`。  
7. 个人客户开了 `CHECKPWDFLAG` 时解约报文是否带了 `Passwd`。

### 11.9 一句话总结

**银行卡解登记 = 全量解约 `checkData` 在 `DELCLIENTBANKACC=Y` 且非预校验时，按 `SIGNOFF_BANKACC` 对 `tbbankacc*` 中未解约/未换卡（可选过滤虚拟卡）的卡逐张调用 `100014`/`100814`/`1L0014`，失败则解约中断，成功后强制回验卡状态；`DELCLIENTBANKACC=N` 时不代发取消登记，改由 `toLocal` 直接把卡置解约。它与 TA 资产账户自动销户是两条独立链路。**

### 11.10 分业务解约 vs 全量解约：银行卡解登记差异

> 核心差异一句话：**全量解约会走「代发 100014 取消登记」链路；分业务解约不发 100014，只在本地从卡上抠掉业务类型，抠空了才把卡状态改成解约。**

#### 11.10.1 全量解约（`checkData` → `toLocal`）

校验阶段就会碰银行卡解登记：

| 步骤 | 行为 |
|---|---|
| 预校验旁路 | `isPreCheck100002` 或 `CHECK_TRANSFER_SWITCH=Y` 时，对每张未解约/未换卡卡做 `PreCheck100014` |
| 正式解登记 | `DELCLIENTBANKACC=Y`（空默认 1）且非预校验、`CheckFlag≠Y` 时进入；再看 `SIGNOFF_BANKACC` |
| 代发交易 | `SIGNOFF_BANKACC=Y` → 逐卡 `pack100014Dataset` + 执行 `100014`/`100814`/`1L0014` |
| 回验 | 同一闸门下强制：名下不能再有「非解约/非换卡」的卡，否则报「有银行帐号未取消登记」 |
| 范围 | 客户（法人行）下**所有**仍正常登记的卡（可过滤虚拟卡） |

本地落地 `toLocal`：

- `DELCLIENTBANKACC=1`：一般**不再**改 `tbbankacc*`（指望 100014 已把卡置解约）
- `DELCLIENTBANKACC=0`：不代发 100014，由 `toLocal` 一次性把卡 `acc_status=解约`、清空 `prd_types`

本质是：**卡级「取消登记」交易（或事先已解登记）+ 强校验卡状态。**

#### 11.10.2 分业务解约（`checkDataByPrdType` → `toLocalByPrdType`）

校验阶段**不碰**银行卡解登记：

- `checkDataByPrdType` 里**没有** `SIGNOFF_BANKACC` / `pack100014` / `PreCheck100014` 逐卡循环
- 最多有 `CHECK_TRANSFER_SWITCH` 的 `transfer` 通知，不是代发 100014
- **不会**因「还有卡未取消登记」而挡解约

本地落地 `toLocalByPrdType` 才动卡，且是「抠业务」不是「解登记交易」：

1. 从上送 `BankAcc` 对应那张卡（或未上送卡时客户下全部卡）的 `prd_types` 里，去掉本次 `PrdTypes`
2. `update tbbankacc set prd_types=剩余业务`
3. **仅当**更新后 `prd_types=' '` 时，再 `update acc_status=解约`

示例：卡上签了 `01`（基金+理财），本次只解约理财 `1` → 卡变为 `prd_types=0`，**状态仍正常**，不发 100014。  
若再解约基金把卡抠空 → 本地把该卡置解约，但仍**不是**走 100014 取消登记报文。

#### 11.10.3 对照表

| 维度 | 全量解约 | 分业务解约 |
|---|---|---|
| 是否代发 100014/100814/1L0014 | 受 `SIGNOFF_BANKACC` 控制，可代发 | **不代发** |
| `PreCheck100014` 预校验 | 可走 | **不走** |
| 「有银行帐号未取消登记」回验 | `DELCLIENTBANKACC=Y` 时有 | **无** |
| 卡处理对象 | 名下全部仍登记卡（批量） | 上送卡，或未上送时批量抠业务 |
| 卡状态何时变解约 | 100014 成功后，或 `DELCLIENTBANKACC=0` 时 toLocal 一把改 | **仅当该卡 `prd_types` 被抠空** |
| 卡上仍有其它业务时 | 全量目标是整客户解约，卡也要处理完 | 卡可继续正常，只少一类业务 |
| 关键参数 | `DELCLIENTBANKACC`、`SIGNOFF_BANKACC`、`T100002_SIGNOFF_100814`、虚拟卡过滤等 | 基本不依赖上述解登记参数；靠 `SIGN_BY_PRDTYPES` + 上送 `PrdTypes` |

#### 11.10.4 实务含义

- 要「解约顺带取消银行卡登记（发 100014）」→ 必须走**全量解约**，并配好 `SIGNOFF_BANKACC`（及通常 `DELCLIENTBANKACC=1`）。
- **分业务解约**只改签约业务标记；卡要真正「解登记」需另做 100014，或等到该卡业务被解到空、由 `toLocalByPrdType` 本地置解约状态（仍不是 100014 报文）。
- 分业务若客户只剩最后一类业务，且数量条件使其**不**再走 `signOffByPrdType=true`（代码里「不是最后一个业务」才分业务），则会落到**全量**分支，那时才会出现 100014 解登记逻辑。
