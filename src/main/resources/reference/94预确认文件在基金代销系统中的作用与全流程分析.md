# 94预确认文件在基金代销系统中的作用与全流程分析

## 1. 94文件的业务定位

94文件是基金代销系统中的**预确认文件**，核心作用是：在正式确认前，先把TA返回的预确认结果导入系统，驱动当日/次日的划款汇总与自动划拨链路。

在当前实现中，94链路对应以下批量交易码：

- `210602`：取预确认文件（`PUB210602`）
- `210603`：预确认文件数据导入（`PUB210603` + `DXFUND210603`）
- `210604`：预确认汇总划款数据（`PUB211604` + `DXFUND210604` + `PUB210604`）
- `210625`：资金划拨数据汇总（`PUB210625`）

配置入口：`app/sql/sql-dxfund/pub/dxfund/extradata/94preCfm/preCfm.sql`

---

## 2. 初始化配置（`preCfm.sql`）做了什么

`preCfm.sql` 不是业务处理SQL本体，而是把“94文件处理能力”挂到系统上，主要包含4类配置。

### 2.1 文件字段映射（`tbfieldmap`）

将文件模板 `ZD21` 的 `94` 文件字段映射到系统字段，例如：

- `serial_no`（申请单编号）
- `curr_type`（币种）
- `prd_code`（基金代码）
- `trans_date`（交易发生日期）
- `amt`（申请金额）
- `busin_code`（业务代码）
- `asset_acc`（基金账号）
- `err_code` / `err_msg`（返回码/返回信息）

这一步为后续 **公共侧按模板读文件** 与 **交易侧按表入库** 提供字段对应关系；业务行数据最终落在 **交易片区库** 的 `tbdxfundpretranscfmtmp`（该表建表脚本在 `sql-dxfund/trans` 交易库结构中，不在公共片区 SQL 目录）。

### 2.2 文件类型注册（`tbfiletype`）

把 `file_type='94'` 的目标表登记为 `tbdxfundpretranscfmtmp`，并约定文件名规则：

- `OFD_SSS_RRR_YYYYMMDD_TT.TXT`

同时配置 **`area_type='1'`**（交易片区文件类型）：与公共 `TaFileReader` 中「直导列表 / 格式化列表」的分流一致——94 走 **格式化 + 分片下发** 链路，而不是公共侧 `area_type='0'` 的直导入库路径。

### 2.3 交易码注册（`tbtrans`）

注册 4 个批量交易：

- `210602` 取预确认文件
- `210603` 预确认导入
- `210604` 预确认汇总划款
- `210625` 资金划拨汇总

### 2.4 调度编排（`tbschedulejob/tbscheduletask`）

按 TA 维度建立串行依赖：

- `J210602-${TACODE}` -> `J210603-${TACODE}` -> `J210604-${TACODE}` -> `J210625-${TACODE}`

并把任务分发到公共片区和交易片区服务：

- 公共：`lcpt-dxfund-pub-batch`
- 交易：`lcpt-dxfund-batch-trans1/2`

## 3. 全流程数据链路（取文件 -> 导入 -> 业务处理）

## 3.1 取文件阶段（210602 / `TPUB210602HSAdapter`）

代码：`T210602HSAdapter`

处理要点：

1. 构建本地目录：`<IFMBASEPATH>/data/<taCode>/recv`
2. 解析远端目录：优先读取 `210602_${TACODE}.ServerPath`，其次 `210602.ServerPath`，再回退 `210101*`
3. 支持 `YYYYMMDD` 占位替换为当前业务日
4. 通过 `TaFileReader.getFileFromServer` 拉取文件
5. 强制必取文件类型：`94`
6. 校验文件并登记 `tbfileinfo`

关键参数分支：

- `ALLOW_PRE_CFM_FILE_NOT_EXIT=1`：允许94文件不存在时不报错直接返回
- `PRE_CFM_FILE_USE_PRE_DATE=1`：按TA工作日逻辑，支持T日取TA上一个工作日文件

> 结果：文件到本地 + 文件元信息入库（供后续导入识别）

---

## 3.2 导入阶段（210603）

分两层（调度上为 `J210603-${TACODE}T01` → `T02`，先公共后交易）：

- 公共层 `TPUB210603HSAdapter`（`PUB210603`）：按 `tbfiletype.area_type` 分流——对 94 主要为 **格式化、按交易片区拆文件、`sendAreaFile` 下发**；**不在公共库写入** `tbdxfundpretranscfmtmp`。
- 交易层 `TDXFUND210603HSAdapter`（`DXFUND210603`）：接收公共产出的分片文件，**写入交易库** `tbdxfundpretranscfmtmp`，再执行 **`cfmDataFormat()` 业务标准化**。

### 3.2.1 公共层（`TPUB210603HSAdapter` / `PUB210603`）

公共批量中的 `TaFileReader` 用 **`tbfiletype.area_type`** 区分两类文件（与 `file_dir`「日终/日启/导出」不是同一维度）：

| 列表方法 | SQL 中 `area_type` | 含义 |
|----------|-------------------|------|
| `getLoadDataFileList()` | `'0'` | **公共片区直导**：命中则走 `loadDataFileRecord`，在本进程连接的数据库按 `table_name` 入库。 |
| `getForamtDataFileList()` | `'1'` | **交易片区文件**：命中则走 `formatDataFileRecord`，读 TA 原始文件、格式化并按片区生成待下发文件，再 `sendAreaFile`（含 DFS 及可选 FTP 等到各 `AreaFile_*`）。 |

`preCfm.sql` 将 94 配为 **`area_type='1'`**，因此对 94 而言：

1. **`getLoadDataFileList()`** 通常 **不包含** 94（除非另行配置了 `area_type='0'` 的重复登记，一般不应如此）。
2. **`getForamtDataFileList()`** 会包含 94，进入格式化链路。
3. **`deleteTmpRecord(context, impDataFileList)`** 仅针对 **直导列表** 中的文件解析出的目标表做清理；94 不在该列表时，**不会因 94 在公共侧删除** `tbdxfundpretranscfmtmp`（且公共库通常无此表）。
4. **`loadDataFileRecord(impDataFileList)`** 对 94 常为 **空列表跳过**；真正针对 94 的是 **`formatDataFileRecord(formatDataFileList)`**。
5. **`sendAreaFile`**：把分片后的文件送到各交易片区，供下一步 `DXFUND210603` 消费。

**小结**：公共 210603 对 94 的准确表述是 **「预处理：格式化 + 分片 + 跨片区发送」**；分析业务落表时应看 **交易侧** `tbdxfundpretranscfmtmp`，而不是公共片区是否建该表。

### 3.2.2 交易层（`TDXFUND210603HSAdapter` / `DXFUND210603`）

交易批量使用 **另一套** `TaFileReader`：`getLoadDataFileList()` 通过公共接口 **`getFileInfoFileNameList`** 查询 `tbfileinfo` + `tbfiletype`，且 **`area_type` 固定为交易片区**（与字典 `K_GSPQ_TRANS`，值为 `'1'` 一致），从而拿到 **已由公共格式化并下发到本片区路径** 的文件列表。

核心动作顺序：

1. **`deleteTmpRecord`**：按上述列表解析出的目标表（含 `tbdxfundpretranscfmtmp`）在 **本交易库** 清理当日相关数据。
2. **`loadDataFileRecord`**：将分片文件数据 **写入交易库** `tbdxfundpretranscfmtmp`。
3. **`cfmDataFormat()`**：在入库完成后做业务修正与明细汇总（见下）。

在 `cfmDataFormat()` 中执行关键修正：

```sql
update tbdxfundpretranscfmtmp set cfm_date = :init_date where cfm_date = 0;
update tbdxfundpretranscfmtmp set cfm_amt = amt;
```

因为94文件天然缺失“确认日期/确认金额”，系统用导入日和申请金额补齐。

然后根据 TA 是否“仅明细/带汇总”处理 `detail_flag`，并在需要时将多条明细归并为汇总记录（经 `tbdxfundsumdetail` 中间表）。

补充逻辑：

- 若开启投顾映射，会把匹配份额的记录更新 `advisor_flag='1'`

> 结果：交易库中 `tbdxfundpretranscfmtmp` 从「分片文件导入后的原始行」经标准化，变为「可用于划款汇总的标准预确认态」。

## 3.3 预确认汇总划款阶段（210604）

### 3.3.1 公共校验（`PUB211604` / `TPUB211604HSAdapter`）

校验 94 场景产品参数合法性：

- 使用94生成划款的产品（`control_flag` 第173位=1）
- 若产品结算方式是净额（`square_way='1'`）则报错

原因：94文件没有完整手续费字段，净额模式会导致日间与日终自动划拨口径不一致。

### 3.3.2 交易片区汇总（`DXFUND210604` / `TDXFUND210604HSAdapter`）

在交易片区先从 `tbdxfundpretranscfmtmp` 生成中间汇总：

1. 生成 `tbdxfundtranssum`（按产品/业务码汇总）
2. 生成 `tbdxfundpayment`（按产品聚合划款金额）
3. 同步到 `tbdxfundpaymentsync`、`tbdxfundtranssumsync`
4. 导出标准文件并发送给公共片区

关键SQL意图（简化）：

```sql
insert into tbdxfundtranssum (...)
select ..., sum(cfm_amt), sum(cfm_vol), sum(charge), sum(back_fee)
from tbdxfundpretranscfmtmp
where cfm_date=:init_date
  and err_code=:ta_succ_code
  and busin_code is not null
group by prd_code, ta_code, busin_code, curr_type;
```

```sql
insert into tbdxfundpayment (...)
select ..., sum(cfm_amt)
from tbdxfundtranssum
where busin_code in ('120','122','139','887')
group by prd_code, ta_code, curr_type;
```

参数开关：

- `TRANSSUM_AND_PAYMENT_CFM_AMT_NOT_CONTAIN_AR=1` 时，`advisor_flag='1'` 的金额不计入 `cfm_amt`

### 3.3.3 公共片区汇总（`PUB210604` / `TPUB210604HSAdapter`）

公共片区从各交易片区同步文件回灌后，执行全局汇总：

1. 汇总 `tbdxfundpaymentsync` -> `tbdxfundprepayment`
2. 汇总 `tbdxfundtranssumsync` -> `tbdxfundtranssum`
3. 补齐币种、产品经理、费用等派生字段

> 结果：形成后续自动划拨所需的统一预划款口径数据。

---

## 3.4 资金划拨汇总阶段（210625 / `TPUB210625HSAdapter`）

`210625` 调用 `T210625AutoTransfer.calAutTransferAmt()`，将预确认汇总数据变成自动划拨指令。

核心目标表：

- `tbdxfundautotransfer`（划拨主表）
- `tbdxfundautotransferdetail`（划拨明细）

核心来源表：

- `tbdxfundprepayment` / `tbdxfundprepaymentorg`
- `tbdxfundtranssum`
- 产品与账户参数表（`tbdxfundproduct`、`tbdxfundprdbankacc`、`tbprdparamvalue`）

业务语义：

1. 先清理当日 `real_flag='1'` 的自动划拨数据
2. 汇总认/申购款（`amt_usage=1/9` 或统一口径）
3. 可选汇总手续费款（`amt_usage=2`）
4. 可按TA级再聚合（`prd_code='000000'`）
5. 明细保留到 `tbdxfundautotransferdetail`

关键参数：

- `AUTO_TRANSFER_ISCAL_FEEMAT`：是否汇总手续费划拨
- `FUND_AUTOTRANSFER_USAGE_FLAG`：认购/申购款用途是否拆分
- `PAY_CLT_TYPE`：是否区分个人/机构客户划拨
- `SHOW_SIGN_SYSNO`：支付系统编号展示口径
- `FLAG_PRE94_NO_ESTAB_PRD`：募集期不给94时，是否仍生成标准划拨记录（兼容特殊TA）

## 4. 一张“数据流动图”（按表）

```text
TA 94文件
  -> 本地recv目录 + tbfileinfo
  -> PUB210603：格式化/分片 + sendAreaFile（tbfiletype.area_type=1）
  -> TDXFUND210603：分片文件 -> 交易库 tbdxfundpretranscfmtmp + cfmDataFormat
  -> tbdxfundtranssum/tbdxfundpayment         (210604交易片区生成)
  -> tbdxfundtranssumsync/tbdxfundpaymentsync (210604交易片区同步)
  -> tbdxfundprepayment + tbdxfundtranssum    (210604公共片区汇总)
  -> tbdxfundautotransfer/detail              (210625资金划拨汇总)
```

## 5. 94文件在系统中的核心价值总结

1. **连接“交易结果”与“资金清算”**：94预确认是日间资金划拨的关键输入。
2. **提升日启/分TA处理能力**：支持按TA工作日取数、缺文件容错、分片汇总。
3. **形成可控口径**：通过参数开关控制是否纳入投顾、手续费、募集期特殊场景。
4. **支持跨片区一致性**：交易片区先算，公共片区再汇总，最终统一进入自动划拨表。
5. **与标准划拨链路衔接**：当94不足或TA差异化时，可借参数回退/补充标准逻辑。

---

## 6. 关键排查点（运维/联调常用）

- `210602` 后无文件：先看 `ServerPath` 配置与 `ALLOW_PRE_CFM_FILE_NOT_EXIT`
- `210603` 后无数据：先确认 `tbfiletype` 中 94 的 `area_type`（默认可为 `1`）；公共侧看 `formatDataFileRecord` / `sendAreaFile` 是否执行成功，交易侧看 `DXFUND210603` 是否拿到分片文件及 `tbfieldmap` 与 TA 模板是否一致
- `210604` 金额异常：检查 `err_code` 成功码、`TRANSSUM_AND_PAYMENT_CFM_AMT_NOT_CONTAIN_AR`
- `210625` 无划拨：检查 `tbdxfundprepayment` 是否有数据，以及 `AUTO_TRANSFER_ISCAL_FEEMAT`、`FLAG_PRE94_NO_ESTAB_PRD`
- 94产品报错：检查 `PUB211604` 对应的产品结算方式是否违反“全额交付”要求
